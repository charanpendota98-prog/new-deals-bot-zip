1. ARE OUR LINKS BEING POSTED? - ONE NUMBER, AND IT IS NOW TRUSTWORTHY
===========================================================================
  The auditor used to say "bit.ly is a third-party shortener". That literal
  predates the 2026-09-06 policy under which every list post carries OUR Bitly
  links by design - so it flagged healthy posts, and `--strict` cried wolf. A
  false alarm is how a real one gets ignored, so ownership is now read from the
  DATA:

    * the bot's OWN link_cache (the same rows the pipeline's provenance gate
      consults when it decides a link is ours), and
    * our EarnKaro publisher id, read from $EARNKARO_PUBLISHER_ID, the token in
      $EARNKARO_API_KEY, or the gitignored ops/.earnkaro_key (never printed).

  RUN IT:

      python3 ops/quality_audit.py --db bestgaa/bestgaa.sqlite3 --limit 200

      QUALITY AUDIT | db=... posts=200 findings=0
        LINK PERFECTION | links=137 our-short=88 our-publisher=12 unattributed=0 clean-merchant=37 FOREIGN=0
        every published link is one of ours (minted by this bot, our tag, or a
        clean merchant page) - nothing foreign reached a channel

      python3 ops/conversion_report.py          # the live window, same counts
        LINKS    : WORKING - 137 published link(s), all ours (88 short, 12 tagged,
                   37 clean merchant)
        # or: LINKS    : NEEDS ATTENTION - 2 foreign link(s) reached a channel
        #     -> python3 ops/quality_audit.py --strict   (it names the queue ids)

  WHAT THE BUCKETS MEAN
    our-short        a link THIS bot minted (EarnKaro / HYPD / Bitly / is.gd).
                     Bitly and is.gd links are proven by their link_cache row -
                     not by their domain - because other channels post bit.ly
                     links too. That is the whole point of asking the data.
    our-publisher    our Amazon tag, or our EarnKaro publisher id
                     (affExtParam2=5478322).
    unattributed     a Flipkart or Myntra page with NO publisher id. The product
                     opens and pays NOBODY - and unlike a clean merchant page it can
                     be fixed (the network's affExtParam2 works on the page itself).
                     New posts stamp it automatically (v18.5); this bucket is how the
                     old, commission-losing posts are still counted and named.
    clean-merchant   a store page kept ON PURPOSE because the network has no
                     campaign AND the page itself carries no attribution we may
                     stamp (e.g. Meesho/AJIO). It earns nothing and the report says
                     so; it is not a defect.
    FOREIGN          a link that should never have left: the source's own short
                     link, another channel's bit.ly, a stranger's tag or id.
                     `--strict` exits 1 on it; the detail line names why.

  Exit codes: 0 = clean (or nothing to audit), 1 = findings AND --strict.
  diagnose.sh section 10 and deploy_and_verify.sh section 5 both run the auditor,
  so the verdict shows up in the normal deploy/verifications without new commands.


2. A NEW REDIRECT DOMAIN NO LONGER COSTS A COMMISSION (EK VERIFIED)
===========================================================================
  `earnkaro_output_kind()` can only call a link ours when it recognizes the
  network's short domain. Affiliaters adds and renames them, and the old answer
  for an unknown one was:

      EK REJECT | API response is not an attributable affiliate link
      -> the deal posts with a clean merchant link and earns NOTHING

  - indistinguishable from "this store has no campaign". Now a short-link-SHAPED
  output is FOLLOWED and accepted only when its destination proves it:

      EK VERIFIED | unknown short domain enkr.link resolves to www.myntra.com
                  (attribution travels in the redirect, as ekaro.in does)
      EK VERIFIED | unknown short domain enkr.link resolves to www.flipkart.com
                  carrying OUR publisher id

  ACCEPTED only when:
    * the destination is a known merchant/store page (or a JS-redirect page whose
      markup names one), AND
    * it is not the source URL, not a foreign shortener/echo domain, not a
      non-shop wrapper, AND
    * if it shows an affExtParam2, that id is OURS - and for Amazon, its tag is
      OUR tag.

  STILL REFUSED (unchanged, and pinned by tests):
    * a bare merchant-page echo (HTTP 200 is not a conversion),
    * a destination carrying somebody else's publisher id  -> `EK REJECT ... FOREIGN attribution`
    * a short link that only leads back to the source URL,
    * a short link that leads to a foreign shortener (amzn.to etc),
    * a short link that does not redirect at all (nothing was proven),
    * an Amazon destination without our tag.

  Watch it live:

      journalctl -u bestgaa -f | grep -E 'EK VERIFIED|EK REJECT|EK SUCCESS|EK MISS'
      # ops/conversion_report.py also counts EK VERIFIED as its own marker now

5. WHY COMMISSIONS WERE MISSING (2026-10-04) - AND WHAT CHANGED (v18.5)
===========================================================================
  USER REPORT
    "CHALA VARAKU MANAM MISS AVUTHUNNAM COMMSION ASALU RAVATLEUD NDHUKU ANTE
     LINKS ANNI MARIPOTHUNNAI INVALID LINK SVASTHUNNAI PRODUCT OPEN AVUTHUNDI
     KAANI ADI MANA LINKS KADU"

  WHAT WAS WRONG (found in the source, not guessed)
    When the affiliate network answered "no campaign for this store", the bot
    published the BARE merchant page on purpose (a deal must not be lost). The
    page opened - and paid nobody. Two places did this:
      1. bestgaa/main_bot_new.py -> keep_passthrough()  (Telegram channels)
      2. tg-wa-bridge/bridge.js -> direct-source safety-net jobs that resolve a
         raw source link and post the merchant page unconverted (WhatsApp)
    Nobody's id was on the link, so the click was worth zero: "product open
    avuthundi kaani adi mana links kaadu" - exactly the complaint.

  WHAT CHANGED
    For the Flipkart family the network's own attribution parameter works on the
    product page itself: `affExtParam2=<publisher>` is the same shape the
    EarnKaro converter returns for this account (the bot already treats it as a
    conversion in earnkaro_output_kind(), and the bridge already treats it as
    proof of "ours"). So where a page would have gone out bare, the bot and the
    bridge now STAMP OUR PUBLISHER ID. A stranger's id on the source page is
    REPLACED, never carried along. Stores with no such contract (Meesho -> HYPD,
    Amazon -> tag, everyone else -> clean page) are untouched:
    EK_ATTRIBUTION_HOSTS defaults to `flipkart.com,myntra.com` and can be
    extended via env ONLY after EarnKaro confirms the store.

  PROOF ON THE SERVER
      journalctl -u bestgaa -f | grep -E 'LINK ATTRIBUTED|UNMONETIZED LINK'
      # LINK ATTRIBUTED | queue=... the product page is posted WITH our publisher id
      #                   (5478322) instead of a bare link that pays nobody: <url>
      python3 ops/quality_audit.py --limit 200 --strict --publisher 5478322
      # unattributed=N counts the OLD posts (pre-v18.5) that opened and paid nobody;
      # watch it stop growing, then re-post those deals manually if they matter.


6. "IDI OPEN CHESTHE VERE VALLA LINK VASTHUNDI" - AMAZON SHORT LINKS (v18.6)
===========================================================================
  USER REPORT
    "https://amzn.to/4dnF9lU?tag=mama086-21 ... IDI OPNE CHESTHE VERE VALLA LINK
     VASTHUNDI. ASALU ALAGA AVODDU. PERFECTGA JUST TAG MARISTHE VUNNA LINK CHETHE
     ALAGA AKDU - LONG LINK LO MARCHI SHORTEN GA CHESI POST CHEYALIGAA"
    also: "https://www.amazon.in/dp/B0D9P2M1PB?th=1&smid=...&tag=dv12399-21"

  WHAT WAS WRONG
    `amzn.to/XXXX` is a short code that belongs to WHOEVER CREATED IT. Our tag glued
    on the end does not change where it goes: the reader lands on that person's page
    (their attribution travels in the redirect) and we earn nothing. A raw
    `amazon.in/...?tag=dv12399-21` is the same disease with the tag visible.

  WHAT CHANGED (both runtimes)
    * bot: `is_amazon_short_host()` marks amzn.to / amzn.in / amzn.eu / a.co as
      WRAPPERS. They are resolved to the long amazon.in product page, re-tagged with
      OUR Associates tag, compacted and then SHORTENED with our own shortener.
    * bot: `SHORTEN_AMAZON_LINKS=true` (default) - a single Amazon deal is shortened
      too, not only list links. The fallback when the shortener cannot answer is the
      compact `amazon.in/dp/ASIN?tag=OURS` page (never the source's short code).
    * bot: `cut_amazon_short_links()` runs at DELIVERY as well, so a post rendered by
      an older build still cannot publish a short code: the link is cut, the deal
      text goes out, and the log says why (`AMAZON SHORT CUT | queue=...`).
    * bridge (WhatsApp safety-net jobs): `prepareAmazonShortLinks()` resolves or BLOCKS
      every Amazon short link before the policy gate; an unresolved one is a permanent
      refusal, so it is never retried and never published. `needsShortening()` now
      returns true for a link carrying OUR tag, so the channel shows a short link.
    * a stranger's tag (`dv12399-21`) never survives the rebuild, and only a link that
      actually carries OUR tag may be shortened (cloaking an untagged page is refused).

  FOR THE REVIEW CHANNEL: `t.me/smartbuyhub11` still sees the DIRECT tagged product
  page, because every short link we mint is recorded (`_short_to_long`) and expanded
  back on that one target - a reviewer never has to follow a redirect.

  PROOF ON THE SERVER
      journalctl -u bestgaa -f | grep -E 'AMAZON LINK SHORTENED|AMAZON SHORT (CUT|REFUSED)'
      # AMAZON LINK SHORTENED | https://www.amazon.in/dp/ASIN?tag=OURS -> https://bitli.in/XXXX
      # AMAZON SHORT CUT | queue=... removed 1 Amazon short link(s) (a short code is
      #   somebody's wrapper, never our destination)
      python3 ops/quality_audit.py --limit 200 --strict
      # an amzn.to link in a published post is a LINKS finding ("the source's own
      # Amazon short link was posted instead of ours") - it must stay at 0
  Set SHORTEN_AMAZON_LINKS=false / WA_SHORTEN_AMAZON_LINKS=false to spend no
  shortener quota on Amazon (the compact tagged page is then posted).


7. "COMMSION ASALU MISS AVODDU" - THE LAST TWO PLACES A CLICK COULD PAY NOBODY
===========================================================================
  Two more holes were closed after the v18.6 report; both keep the deal AND the
  commission:

  (a) HYPD link that turns out NOT to point at Meesho. Our HYPD ID is Meesho-only,
      so the share link is dropped - and the verified merchant page used to be
      published BARE. If that page is a Flipkart/Myntra page it now carries our
      publisher id instead:  LINK ATTRIBUTED | HYPD out of scope for <host> ...

  (b) WhatsApp bridge, BOT-FED posts. A row rendered before v18.5 (or the
      degraded-post path when the API never answered) can still carry a bare
      Flipkart/Myntra page. `attributeBareMerchantPages()` now stamps our
      publisher id on it at display time - the provenance check still sees the
      URL the bot cached, the deal text is untouched, and the reader lands on the
      page with OUR id:  LINK ATTRIBUTED | bare merchant page ... not free
      A page already carrying our id, a stranger's id, a Meesho page and our own
      short links are all left exactly as they are (pinned by the bridge self-test).
