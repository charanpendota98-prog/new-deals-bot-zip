Reading it:

  * "PAYS US (5478322)"     the returned short link was EXPANDED and its visible
                            attribution is our publisher -> the link is OURS.
  * "MONETIZED (whose account not visible)"
                            the store redirected somewhere unreadable; the token
                            claims above are still the proof of the account.
  * "WRONG ACCOUNT"         the API answered a link that pays somebody ELSE
                            (or a HYPD-attributed page) - replace EARNKARO_API_KEY.
  * "no link" with HTTP 200 a store with no EarnKaro campaign (normal for some
                            marketplaces and for search pages) - that link is
                            posted clean; HYPD is used only for verified Meesho
                            products, never for Shopsy.
  * "TOKEN REFUSED" (401/403)
                            the token was rejected - regenerate it and re-run
                            ops/set_earnkaro_key.sh.

If the endpoint cannot be reached at all (transport error, exit 0 in the HTTP
column), the network - not the key - is the problem; re-run from the server.

In THIS workspace the same command only reaches the token-claims half: the sandbox

sandbox, not the key. The live conversion proof has to come from the server.

2. EARNKARO LINKS ("perfectgaa convert avvatleu")
   -----------------------------------------------
   The converter call is now exactly the documented contract:

     POST https://ekaro-api.affiliaters.in/api/converter/public
     Authorization: Bearer <token>
     Content-Type: application/json
     {"deal": "<clean merchant url>", "convert_option": "convert_only"}

   * `convert_option` was missing. Without it the account-level default decides
     the RESPONSE shape, and a shape the bot could not read meant a post that
     went out unmonetized.
   * Explicit `success=0`/error responses are never rescued by a URL in the
     body; when a whole deal is returned, original source URLs are skipped.
   * The API result must be an attributable network redirect or carry our
     publisher id. A plain merchant-page echo is rejected instead of being
     cached and advertised as a commission link. Flipkart compaction preserves
     `affExtParam2` instead of silently stripping our attribution.
   * Outcomes have distinct markers: `EK SUCCESS`, `EK MISS`, `EK REJECT`,
     `EK AUTH`, `EK HTTP`, `EK NETWORK`, and `EK FALLBACK`. A native Amazon-tag
     fallback is explicitly NOT counted as an EarnKaro conversion.
   * `ops/conversion_report.py` splits these outcomes and no longer reports the
     old ambiguous `EK CONVERT` success lines as no-campaign failures.

   **Account settings matter too:** the API token authenticates the caller but
   does not select a network for each store. In Affiliaters, connect EarnKaro
   under Affiliate Settings > Networks and set the Amazon / Flipkart / Others
   Selections to a network that supports those stores, then save. The official
   pages are https://docs.affiliaters.in/settings/affiliate-settings/networks
   and https://docs.affiliaters.in/settings/affiliate-settings/selections.
   Unsupported store campaigns can genuinely answer no-link.

   To prove a failed post, use its actual product URL rather than the built-in
   sample URLs (which may be unsupported or stale):
     python3 ops/earnkaro_check.py --skip-hypd \
       --deal-url 'https://www.flipkart.com/<actual-product-url>'
     # repeat --deal-url for each actual product link; the token is never printed.

3. THE API KEY (isset perfectly)
   -----------------------------
   The token is a JWT whose payload names the account that gets paid
   (`earnkaro` = the EarnKaro publisher id). The bot now decodes it at startup,
   logs which account earns, pins the foreign-publisher guard to it, and warns
   when the key is not a converter token at all (that warning is the difference
   between "conversion is broken" and hours of guessing).

   Set or rotate it on the server with ONE command (the token is never printed
   and never committed - see the Security section of the README):

     cd ~/bestgaa-bot/bestgaa-bot      # the directory that holds this ops/ folder on the server
     ./set_earnkaro_key.sh '<the token from the Affiliaters/EarnKaro API page>'

   It backs up .env, writes EARNKARO_API_KEY + the publisher id it read out of
   the token, chmod 600, restarts bestgaa and verifies against the live API.

   Check any time:
     python3 ops/earnkaro_check.py --offline     # decode the token, no API call
     python3 ops/earnkaro_check.py               # sample probes + raw bodies
     python3 ops/earnkaro_check.py --skip-hypd --deal-url '<actual failing URL>'
     bash ops/diagnose.sh                        # section 4b prints the current verdict

   Watch conversion outcomes (success, miss, rejection, and fallbacks separately):
     journalctl -u bestgaa -f | grep -E 'EK SUCCESS|EK MISS|EK AUTH|EK REJECT|EK HTTP|EK NETWORK|EK FALLBACK|UNMONETIZED'

     * the channel submitted for Amazon review still shows the DIRECT tagged

   Want the pure native-tag behaviour back (2026-09-06 policy)? Put
   AMAZON_VIA_EARNKARO=false in the bot's .env and restart bestgaa.
